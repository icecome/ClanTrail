**类型**：产品方向 / 概念 / 规划 修订

## 0. 修订摘要（TL;DR）

- **关键转折**：从「无强制账号、纯离线」升级为「**本地优先 + 可选账号**」。账号是增强层，不破坏离线护城河，也不违背原 Non-goal（原写的是「不做强制账号」，不是「永远不能有账号」）。
- **概念升维**：产品定位从「墓地登记工具」→「以族迹为轴的家族记忆传承产品」→ 再加一层「**可选的家族协作网络**」。
- **数据模型**：从「父子树两阶段」改为「**图模型一步到位**」（Person + Relation，支持双系 / 姻亲跨族），修正原清单 v1 树 → v1.1 返工风险。
- **共创策略**：MVP 先做「账号 + 云同步 + 多端备份」；家族多人共创（RBAC / 审核 / 姻亲关联）后置到 P1/P2。
- **护城河重述**：从「数据不出设备」升级为「**数据主权在用户**」——本地为真相源，云端为加密镜像，同步需显式授权，可随时导出 / 销毁。

## 1. 为什么变（Why）

### 1.1 原清单的边界
2026-08-06 的头脑风暴把「离线优先 / 无账号 / 数据不出设备」当护城河，功能聚焦单人：忌日提醒、家族树、照片、备份、离线地图。这套逻辑自洽，但有两个硬伤：

1. **家族是多人事，工具却是单人器**：扫墓、修谱、跨族寻根天然是家族协作行为，纯单机的「数据不出设备」默认把协作可能性堵死。
2. **冷启动难**：DeepSeek 文档也指出，家谱类产品的核心难点是「内容积累慢、冷启动」。单人录入 + 无法共享，增长杠杆弱。

### 1.2 DeepSeek 构想揭示的需求
墓地家谱结合构想中有三块价值原清单没收进去：

- **以族迹为轴，连接两个世界**：物理空间（墓地 GPS）与抽象关系（家谱网络）深度绑定，从「记录一个点」升维到「讲述一个家族故事」。
- **多人共创（类共享文档）**：同家族成员共同编写墓地 / 家谱，需要多角色权限（族长 / 分支编辑 / 成员）、邀请、审核、版本历史。
- **跨族关联（图而非树）**：以「母亲」为桥节点连接李氏与陈氏，一个人可在不同家族有不同「身份坐标」。这要求数据模型是**图**，不是单线父子树。

这三块都**必须靠账号 + 云同步 + 权限体系**才能成立。所以「需要账号」不是推翻原方向，而是把原清单里留好的「可选账号」口子真正打开。

## 2. 产品概念与定位

### 2.1 一句话定位
> **ClanTrail（族迹）** 是一个以族迹为锚点、把「人—墓—关系—记忆」连成一张可跨族延展的图谱的**本地优先家族记忆产品**；默认所有数据留在你设备上，当你愿意时，用可选账号把个人记忆 vault 升级为家族协作网络。

### 2.2 产品概念模型
```
                 ┌─────────────────────────────────────────┐
                 │            ClanTrail（族迹）            │
                 │      本地优先 · 隐私克制 · 可选连接        │
                 └─────────────────────────────────────────┘
                                  │
            ┌──────────┬──────────┼──────────┬──────────┐
            ▼          ▼          ▼          ▼          ▼
         【人 Person】 【墓 Tomb】 【关系 Relation】 【记忆 Event】 【家族 Clan*】
         稳定 ID       GPS 绑定    图边(父/      时间轴/       命名空间/
         双系身份      个人而非    配偶/同胞)   照片/故事    成员/角色*
                      家族                    (* P1 共创)
            │          │          │          │          │
            └──────────┴──── 以族迹为轴 ──┴──────────┘
                                  │
                    离线核心（无账号即可用）
                                  │  可选账号开启
                                  ▼
                    【家族协作网络】（云同步 · E2E 加密 · RBAC）
                    跨族关联（姻亲桥节点）· 多人共编 · 版本历史
```

### 2.3 价值主张分层
| 层 | 给谁 | 价值 | 是否需账号 |
|----|------|------|-----------|
| 个人记忆 vault | 单个用户 | 离线建档、忌日提醒、照片、备份、离线地图 | 否（纯本地） |
| 多端同步 | 同人多设备 | 备份不丢、换机无缝 | 是（可选） |
| 家族协作网络 | 同家族多人 | 共编写谱、跨族关联、版本历史 | 是 |

## 3. 账号体系设计（新增）

### 3.1 三档身份（渐进式 · 本地为真相源）
| 档位 | 名称 | 能力 | 数据落点 |
|------|------|------|---------|
| L0 | 游客 / 本地用户 | 全部离线功能；可查看已加入的共享家族（只读令牌） | 本机 SQLite 为真相源；云端仅加密镜像 |
| L1 | 注册用户（轻量身份） | L0 + 创建 / 拥有家族 + 云同步 + 多设备备份 | 本机 + 云端加密镜像 |
| L2 | 家族成员 | L1 + 家族命名空间 + 角色权限 + 共编 / 审核 | 同 L1 + 家族共享空间 |

**原则**：
- 本地为第一真相源：每个用户的数据首先存在自己设备，纯本地 L0 无任何服务端足迹，离线护城河原样保留。
- 共享是 opt-in：仅当用户「创建家族 / 加入共享」时才加密上云，且只上镜像。
- 游客可「查看」共享家族（只读令牌），但「编辑 / 管理」必须升级为 L1 轻量身份（一键生成密钥，非邮箱 / 密码重注册）。
- 注销只销毁云端镜像 + 服务端身份 + 他人只读令牌，本机数据原封不动。

### 3.2 同步模型（本地优先）
- **真相源在本机**：SQLite 是 source of truth；云端只是加密镜像。
- **异步同步**：注册后开启同步，本地变更经端到端加密（用户密钥，服务端零知识）上传；多设备拉取合并。
- **冲突策略分级**：
  - P1 多端同步（同人）：`last-write-win` + schema 版本号 + 版本历史回滚，足够。
  - P2 多人共编（异人同节点）：再上 CRDT / OT 解决真冲突，避免早期过度工程。
- **显式授权**：同步默认关闭，首次开启需用户确认；随时可停、可导出全量、可销毁云端镜像。

### 3.3 隐私与合规（默认即合规）
- 调起外部地图只传坐标 + 墓地名称，**不传任何逝者信息**（沿用现有约定）。
- 云端镜像端到端加密，服务端无法读取明文。
- 账号不强制实名；密码 / 生物识别本地保管。
- 涉及用户数据的功能（同步、备份导出）主动标注隐私风险。

## 4. 数据模型升级（图模型一步到位）

### 4.1 核心实体
| 实体 | 关键字段 | 说明 |
|------|---------|------|
| `Person` | `id`(稳定 ID)、姓名、生卒、历法、双系标记 | 图节点，一人一 ID，跨家族可复用 |
| `Relation` | `from`、`to`、`type`(parent/spouse/sibling)、`side`(born/married) | 图边，**独立实体**而非字段，支持双向追溯 |
| `Tomb` | `person_id`、`gps`、`cemetery`、`photo_paths` | **绑定个人 ID 而非家族** |
| `Event` | `person_id`、模糊日期、类型、图文 | 生平时间轴 / 故事 |
| `Clan`* | `id`、名称、根 Person | 家族命名空间（P1） |
| `Membership`* | `clan_id`、`person_id`、`role`(族长/分支编辑/成员) | RBAC（P1） |

> *P1 共创阶段引入；P0 先留好实体与字段，不实现 UI。

### 4.2 桥节点示例（母亲跨李 / 陈）
母亲陈氏 = 一个独立 `Person` 节点，拥有两条 `Relation`：
- `side=born`：连陈氏外祖父母（子女关系）
- `side=married`：连李父（配偶）+ 子女（母子/女）

查看母亲个人页时，双入口「娘家族谱 / 夫家族谱」分别渲染以陈氏 / 李氏祖先为根的子图；其 `Tomb` 只存一次，李氏与陈氏地图视图都按各自叙事显示同一坐标。这就是原清单 #2「父子树」无法表达、必须用图模型承载的部分。

## 6. 指标体系统（北极星 + 驱动 + 健康）

### 北极星（沿用并强化）
**关键祭扫节点准时回流率 × 家族档案完整度**
- 回流率：D-1~D+3 活跃 ÷ 应活跃节点
- 完整度：含生卒 / 墓位 / 关系 / 照片的 Person 占比
- 基线建议：提醒开启率 ≥ 40%、家族树创建率 ≥ 30%

### 驱动指标（新增账号相关）
| 指标 | 含义 | 目标 |
|------|------|------|
| 账号激活率 | 注册用户 ÷ 活跃用户 | 验证「可选账号」接受度 |
| 云同步开启率 | 开启同步 ÷ 注册用户 | 衡量连接意愿 |
| 家族创建率 | 建家族空间 ÷ 注册用户 | 共创冷启动 |
| 跨族关联数 | 姻亲桥节点数量 | 差异化护城河强度 |

### 健康指标（护城河监控）
- **纯本地用户占比**：必须长期 > 0，不能因加账号逼走本地用户（护城河报警器）。
- 同步失败率 / 冲突率：P1 上线后重点盯。
- 隐私事件数：目标恒为 0。

## 7. Non-goals（修订）

保留原清单：
- 不做强制账号体系（离线优先为前提）
- 不做 B 端陵园管理（墓位续费 / 园区管理）
- 不做公开社交广场 / 社区
- 不过度商业化（仅纪念册 PDF 精排等克制收费点）

新增 / 强化：
- 云同步默认关闭，必须显式授权；同步内容端到端加密。
- 绝不上传逝者信息到任何第三方；调起地图只传坐标 + 墓地名。
  - 账号不强制实名；不把「登录」作为使用任何离线功能的前置条件。
  - 注销账号只销毁云端镜像与同步设置，绝不删除本机本地数据。
  - P0 不实现多人实时共编（冲突成本高，留到 P2）。

## 8. 风险与待裁决

1. **账号技术选型**：个人开发者，建议轻量自建（已有内嵌 Axum 后端可扩展同步接口），避免重 BaaS 依赖与持续成本。P0 仅做本地身份 + 同步适配器桩，P1 再接云端。
2. **同步冲突策略**：P1 同人多端用 last-write-win + 版本号；P2 异人共编才上 CRDT，避免过度工程。
3. **#P1-7 二维码 vs 离线 NFR**：含照片须联网托管，否则仅几百字节脱敏卡；需裁决是否允许「显式授权的最小托管例外」。
4. **加密锁 PIN 恢复**：不可恢复最纯但会真实丢数据；恢复码引入「码存哪」新问题。
5. **#P0-5 离线地图 ToS**：所选地图服务商是否允许瓦片本地缓存，决定薄兜底还是仅坐标降级。
6. **护城河稀释风险**：加账号后须持续监控「纯本地用户占比」，防止产品悄悄变成强制云端。（已通过「本地为真 + 云端镜像」模型化解：注销只删云端镜像，本机数据持久，协作不侵蚀离线护城河。）
