## Android APK 构建：Gradle 依赖解析根因与修复（进行中）

### 背景
用户要求「检查依赖进度 + 构建 APP 安装包」。三层依赖（前端 npm / Rust 工具链 / Android 工具链）此前已落地，7 个 APP 问题修复已通过 tsc+vite。

### 本次定位的两个根因（均已修复）

1. **`~/.gradle/init.gradle` 的 pluginManagement 作用域错误**
   - 现象：`Could not find method pluginManagement() ... on build of type org.gradle.invocation.DefaultGradle`
   - 根因：`beforeSettings { pluginManagement { ... } }` 未声明闭包参数，pluginManagement 被解析到 Gradle 对象（不存在），而非 Settings。
   - 修复：`beforeSettings { settings -> settings.pluginManagement { ... } }`

2. **AGP 8.11.0 解析直连 dl.google.com 超时（当前主因）**
   - 现象：`Could not resolve com.android.tools.build:gradle:8.11.0` → `Connect to dl.google.com:443 ... timed out`
   - 根因：gen/android 自动生成的 `build.gradle.kts`（buildscript + allprojects）与 `buildSrc/build.gradle.kts` 用 `google()`/`mavenCentral()`，直连本沙箱不可达的 dl.google.com / repo1.maven.org；init.gradle 的 pluginManagement 只管插件，管不到 buildscript classpath。
   - 修复（两处，均幂等，且落在 patch-android.sh 以承受重 init）：
     - `init.gradle` 的 `allprojects` 去掉裸 `google()`/`mavenCentral()`，只留阿里云 `maven.aliyun.com/repository/{google,central}`。
     - `patch-android.sh` 新增第 5 步：把 `*.gradle.kts` 的 `google()`→`maven { url = uri("https://maven.aliyun.com/repository/google") }`、`mavenCentral()`→`maven { url = uri("https://maven.aliyun.com/repository/central") }`。
     - ⚠️ 语法陷阱：`*.gradle.kts` 是 Kotlin DSL，必须用 `url = uri("...")`，不能用 Groovy 的 `maven { url '...' }`。

### 3. SDK 版本不匹配（build-tools 35.0.0 缺失）—— 已确认为死路
- 现象：`Failed to find Build Tools revision 35.0.0`；AGP 8.11.0 把 `buildToolsVersion "34.0.0"` 忽略并强制用 35.0.0，SDK Manager 走 dl.google.com 拉组件超时。
- 验证：本沙箱**无法从任何镜像拉到 build-tools 35.0.0 / platform 35/36 的 zip**：
  - 腾讯云 `mirrors.cloud.tencent.com/AndroidSDK` 是 Nexus 仓库，只代理 `repository2-3.xml`（`/repository2-3.xml` 返回 200），但 `build-tools_r35.0.0-windows.zip` 在根路径 404（Nexus 未代理二进制包）。
  - 清华镜像 `mirrors.tuna.tsinghua.edu.cn/AndroidSDK` 本环境返回 000（不可达）。

### 4. minCompileSdk 35 依赖 —— 真正的硬约束（最终根因）
- `app/build.gradle.kts` 依赖中 `androidx.activity:activity-ktx:1.10.1` 与 `androidx.lifecycle:lifecycle-process:2.10.0` 的 `minCompileSdk = 35`，而其余（webkit 1.14.0 / appcompat 1.7.1 / material 1.12.0）minCompileSdk = 34。
- 结论：**无论 AGP 版本如何，compileSdk 34 都会因这两个依赖被逼迫要 35**；而 35 又需 build-tools 35（本地无、不可达）。降级 AGP 不解决问题，必须一并降级这两个依赖。

### 最终离线方案（零下载，已落到 patch-android.sh 第 7 步）
- ⚠️ **关键：buildSrc 才是 AGP 真实来源**。app 模块 `id("com.android.application")` 无 version，实际 AGP 版本由 `buildSrc/build.gradle.kts` 的 `implementation("com.android.tools.build:gradle:8.11.0")` 决定；仅改根 `build.gradle.kts` 的 buildscript classpath 无效（这就是 build_android6.log 仍报 8.11.0 的原因）。必须两处都改。
- 降级 AGP `8.11.0 → 8.6.0`（根 build.gradle.kts 的 classpath **和** buildSrc/build.gradle.kts 的 implementation，两处），AGP 8.6 接受本地 build-tools;34.0.0（AGP 8.7+ 才强制 35）。
- 降级高 minCompileSdk 依赖：`activity-ktx:1.10.1 → 1.9.0`、`lifecycle-process:2.10.0 → 2.8.7`（二者 minCompileSdk 均回到 34）。
- 配合第 6 步 compileSdk/targetSdk=34 + buildToolsVersion 34.0.0，整链路离线可构建。
- Gradle 8.14.3 / Kotlin 1.9.25 与 AGP 8.6 兼容（AGP 8.6 需 Gradle ≥8.9、Kotlin ≥1.9.10）。

### 5. tauri-android 模块的 compileSdk=36 才是 platform 36 的真正源头（build_android7 失败的根因）
- 现象：build_android7 仍报 `Failed to find Platform SDK with path: platforms;android-36`，且警告 `compileSdk = 36`（即使 app 模块已改 34）。出错任务是 `:tauri-android:generateDebugRFile`。
- 根因：`tauri.settings.gradle` 把 `:tauri-android` 模块的 `projectDir` 指向 **cargo registry 里的 Tauri crate 源码** `…/.cargo/registry/src/<hash>/tauri-2.11.5/mobile/android`（`include ':tauri-android'` + `project(':tauri-android').projectDir = new File(...)`）。该目录的 `build.gradle.kts` 第 8 行硬编码 `compileSdk = 36`——这才是 `platforms;android-36` 需求的来源。它**不在 gen/android 下**，所以前面第 6 步改 app 模块的 compileSdk 管不到它。
- 该文件依赖（core-ktx 1.7.0 / appcompat 1.6.0 / material 1.7.0）minCompileSdk 均远低于 34，降级到 34 不会引发新冲突。
- 修复（两处）：
  - 直接改 `…/tauri-2.11.5/mobile/android/build.gradle.kts` 第 8 行 `compileSdk = 36 → 34`（cargo build 不会重解压覆盖 registry/src 已解压目录）。
  - `patch-android.sh` 新增第 8 步：`find $HOME/.cargo/registry/src -path "*/tauri-*/mobile/android/build.gradle.kts"` → 将 `compileSdk = 36` 替换为 34（幂等，应对 cargo clean 重解压）。
- ⚠️ 注意：改动落在第三方 crate 解压缓存，非项目源码；升级 tauri 版本或 cargo clean 后需重新 patch（第 8 步已自动处理）。

### 6. tauri-plugin-geolocation 路径结构不同 + 改用 Gradle init 钩子（build_android8 失败根因，最终根本方案）
- 现象：build_android8 报错转移为 `:tauri-plugin-geolocation:generateDebugRFile > Failed to find Platform SDK with path: platforms;android-36`。
- 关键差异：geolocation 插件的 android 目录是 `…/tauri-plugin-geolocation-2.3.2/android/`（**无 `mobile/` 子目录**），而 tauri crate 是 `…/tauri-2.11.5/mobile/android/`。所以 patch-android.sh 第 8 步的 `*/mobile/android/build.gradle.kts` 模式**匹配不到 geolocation**，且还有更深的 timing 坑：`patch` 在 `cargo build` 之前运行，那时未解压的插件 crate 根本不在 registry/src 里，find 自然找不到。
- **最终根本方案（推荐，已落地）**：放弃逐个改第三方 crate 文件，改为在 `~/.gradle/init.gradle` 末尾加 Gradle init 钩子，按模块强制 `compileSdk=34`，**不依赖文件路径、也不受 crate 解压时机影响**。
- ⚠️ **旧钩子为何失效（build_android9 仍报 compileSdk=36 的真正原因）**：初版写成
  ```gradle
  gradle.allprojects { project ->
    project.plugins.withId('com.android.library') { project.android.compileSdk = 34 }
    project.plugins.withId('com.android.application') { project.android.compileSdk = 34 }
  }
  ```
  两个致命缺陷：① **Groovy 属性赋值 `project.android.compileSdk = 34` 在 AGP 上不可靠**——AGP 的 `compileSdk` 不是标准 JavaBean setter（无 `setCompileSdk()`），Groovy 的 `x.prop=34` 会去找 `setProp()` 失败；Kotlin DSL 的 `compileSdk = 34` 实际调用的是 `compileSdk(int)` 方法。② **`withId` 回调时序**：回调在插件 applied 时**立即**触发，早于模块的 `android {}` 配置块，所以 34 先被设上、随后被 build.gradle.kts 里的 `compileSdk = 36` 覆盖（警告里仍是 36）。
- ✅ **正确写法（已落地，build_android10 验证中）**：用经典 Groovy DSL `compileSdkVersion 34` + `afterEvaluate`（保证在所有 `android {}` 配置块之后强制生效，34 必定胜出）：
  ```gradle
  allprojects {
    afterEvaluate { p ->
      def isAndroid = p.plugins.hasPlugin('com.android.library') || p.plugins.hasPlugin('com.android.application')
      if (isAndroid) {
        p.android.compileSdkVersion 34
        p.android.buildToolsVersion '34.0.0'
      }
    }
  }
  ```
- ⚠️ **隐藏层 `.tauri/tauri-api`**：每个插件 android 目录下还有 `android/.tauri/tauri-api/build.gradle.kts`（Tauri 自动生成的 tauri-api 子项目），同样硬编码 `compileSdk = 36`。批量 find `*/android*/build.gradle.kts` 时一并改掉（geolocation、opener 的 `.tauri/tauri-api` 均发现并清零）。
- 冗余兜底：文件级把所有已解压的 Tauri crate android `build.gradle.kts` 的 `compileSdk = 36 → 34`（含 `.tauri/tauri-api`），cargo build 不重解压覆盖 registry/src。
- 结论：init 钩子（afterEvaluate + compileSdkVersion）会统一覆盖 tauri、geolocation、opener 及任意其它 Tauri 插件的 android 模块，使全部使用本机 `platforms;android-34`（无需下载任何 35/36 组件）。`targetSdk` 这些插件均未显式声明，默认跟随 compileSdk=34，不会触发 `targetSdk>compileSdk` 冲突。

## 移动端 BottomSheet 键盘适配修复（2026-08-08 晚）

用户反馈「新建家族」底部弹窗在输入法弹出时：① 首输入框聚焦会遮挡下方两个输入框；② 点击第三个介绍输入框会导致背景主界面上移。

**根因**：`BottomSheet` 为 fixed 定位贴底面板，无键盘高度感知与背景滚动锁定；浏览器/ WebView 默认滚动行为会滚动 document（背景主界面）。

**改动：**
1. `web/src/components/BottomSheet.tsx`：
   - 弹窗打开时锁定 `body` 与 `.app-shell` 滚动，记录并恢复滚动位置，防止背景主界面上移。
   - 监听 `window.visualViewport` resize/scroll，计算键盘高度（`window.innerHeight - visualViewport.height`），设置 CSS 变量 `--keyboard-offset`。
   - 输入框 focusin 时 `scrollIntoView({ block: 'nearest' })`，确保当前输入框在弹窗可视区内。
2. `web/src/styles.css`：
   - `.sheet` 增加 `transition`、双回退 `max-height: 85vh/85dvh`、`display: flex; flex-direction: column`。

   - `.sheet-body` 增加 `overflow-y: auto`、`overscroll-behavior: contain`、`-webkit-overflow-scrolling: touch`、`flex: 1`，使多输入框时在弹窗内滚动。

- 修复移动端 APP 可滑动页顶部内容穿透状态栏问题：将 .app-header 从 background: transparent 改为纸底磨砂背景 rgba(244,241,234,0.82) + blur，sticky 时遮挡滚动内容，避免进入系统通知栏。vite build 通过，并用 .cache/statusbar-test.html 做透明/磨砂对比验证。

## Bug 修复

### 1. 图片上传失败（Android WebView multipart 缺陷）
- **根因**：Tauri Android WebView 的原生 `fetch()` 在跨域发送 `FormData` 时，未正确生成 multipart boundary，导致 Axum multer 解析失败。
- **修复**：后端新增 `/api/images/upload64` 接口接收 base64 JSON（`src-server/src/lib.rs`），前端 `uploadImage` 签名改为接收 `File`，Tauri 环境走 base64 上传，非 Tauri 环境保持 multipart。
- **涉及文件**：`src-server/Cargo.toml`（加 base64 依赖）、`src-server/src/lib.rs`、`web/src/api/client.ts`、`web/src/pages/GraveDetailPage.tsx`

### 2. 返回手势逻辑错误（Tab 切换污染历史栈）
- **根因**：底部 Tab 切换使用 `navigate(path)`（push 模式），每次切换 Tab 都 push 一条历史记录，Android 返回键按浏览器历史回退时在 Tab 之间跳转。
- **修复**：`App.tsx:121` 改为 `navigate(t.path, { replace: true })`，Tab 切换不 push 历史，返回键只在页面层级间导航。
- **涉及文件**：`web/src/App.tsx`

### 3. 上传按钮无反应 / 整页双指缩放 / 地图显示不全
- **根因 1**：`display:none` 的 file input 通过 `ref.current.click()` 触发，在 Android WebView 中常被安全策略拦截，导致点击无反应。
- **修复 1**：`GraveDetailPage.tsx` 把 file input 改为透明覆盖层（`opacity:0` + 绝对定位）直接让用户点击；`styles.css` 新增 `.upload-btn` / `.upload-input-overlay` 样式。
- **根因 2**：`index.html` 的 viewport 未禁用用户缩放，双指手势被 WebView 解释为整页缩放，导致 Tab 栏也被放大。
- **修复 2**：viewport 增加 `maximum-scale=1.0, user-scalable=no`。
- **根因 3**：`.map-tool-screen` 未显式声明 flex column，天地图初始化时容器尺寸可能为 0，仅渲染部分瓦片。
- **修复 3**：`.map-tool-screen` 显式 `display:flex; flex-direction:column; height:100dvh`；`MapPage.tsx` 初始化后用 `requestAnimationFrame` + `setTimeout` 两次 `resize()`，确保布局稳定后重新渲染瓦片。
- **涉及文件**：`web/src/pages/GraveDetailPage.tsx`、`web/src/styles.css`、`web/index.html`、`web/src/pages/MapPage.tsx`
- **验证**：`npm run build` 通过（tsc + vite）。
- 修复状态栏重叠：根因是 .app-header 用 sticky 但实际滚动容器是 .main-content，sticky 不生效。改为 position: fixed + .app-screen 统一预留 calc(var(--safe-top) + 52px) 顶部空间，.main-content 改为 overflow:hidden 避免双重滚动。vite build 通过，验证截图显示状态栏文字清晰、内容被顶栏遮挡。
- 修复移动端 APP 无法滚动的问题：根因是 .main-content overflow:hidden 且 .app-screen 自身 overflow-y:auto 但高度未受限，导致没有滚动条。修复为 .main-content overflow-y:auto 作为滚动容器，.app-screen 去掉 overflow-y:auto 仅保留 padding-top 为 fixed header 留位，min-height 从 100dvh 改为 100
